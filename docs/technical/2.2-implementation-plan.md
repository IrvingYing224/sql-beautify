# SQL Beautify 2.2 全量审计整改实施计划

状态：Wave 0–30 已完成；后续工程复审整改见文末 2026-10-01 补充记录，版本仍为本地 `2.2.0` 候选

设计：[`2.2-audit-remediation-design.md`](2.2-audit-remediation-design.md)

目标：所有审计项完成处置并通过完整回归、性能与打包门后，统一形成一个本地 `2.2.0` 发布候选。

## 1. 执行规则

- 同一 worktree 的 build/test 始终串行；只有互不写共享 artifact 的只读检查可以并行。
- Wave 0 文档提交完成前禁止修改生产代码。
- 每个实现波次先补能在基线上失败的 regression/measurement，再实现，再跑 targeted gate；失败断言
  与所属修复在同一波次提交，任何本地提交都不得让维护测试集保持红色。
- “待验证”项先建立最小复现；证伪时提交契约测试和设计文档处置结果，不为满足审计文字制造行为变化。
- 不通过的 performance gate 必须定位 operation count、workload 或环境原因；不得只放宽阈值。
- 每波只创建一个可解释、可回退的本地提交；跨波次问题使用后续聚焦提交，不 amend 已完成边界。
- package/lock/CHANGELOG 的版本只在最终 release wave 一次性改为 `2.2.0`。
- 当前 package/lock 已是尚未发布的 `2.2.0`；补充 Wave 不重复 bump 版本，所有新增修复仍并入同一候选。
- 本计划授权仓库内代码、测试、文档、stage 和本地提交；不授权 push、tag、Release、workflow dispatch、
  历史改写或删除用户数据。
