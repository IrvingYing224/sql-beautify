## 1. 背景与诊断

2026-10-21 对 2.2.1 做了一次全面审视（黑盒探测 331 个精选用例加 1.3 万个扰动用例，另做 3 万条 fuzz，并对 core、适配层、工程分别做了静态审查）。结论分两面。

**骨架是对的，承诺也兑现了。** 2.x 的流水线（无损 lexer → CST → analysis index → Layout IR → 单一 renderer → token 等价校验）和 Prettier、gofmt 属于同一家族。实测中 token 被改写 0 次、部分提交 0 次。1.x 那种"文本 → 文本"的 pass 链（`lib/core/sql-format-pipeline.js` 的 `current = passes[i](current)`）才是结构性错误，2.x 换掉它是正确的。

**反复出 bug 的根源在三个"重心"偏差上，而不在骨架：**

1. **只有安全有规格，排版没有规格。**
   - AGENTS.md 的规则几乎都是 fail-closed、权威归属、不得改写，没有一条规定输出应该长什么样。
   - 3,640 个 assert 里，比对格式化输出文本的约 150 个（约 4%）。
   - 公共语料 25 个文件，只比对 status 和 token 指纹。
   - 这次查出的缺陷全部是排版规则问题（附录 C），而 token 等价、invariant oracle 在原理上看不见排版错误。
2. **闭世界加二元结果。** 要么完整建模后格式化，要么原样保留并给出 warning。
   - 每补一个构造要改 15–18 个文件（parser、CST 节点、契约、analysis、4 个 oracle、layout、registry）。
   - 真正做排版决策的代码只占 core 约 10%。
   - 结果是 `div`、`nulls last`、`limit … offset`、`use db;` 这类日常写法长期得不到格式化。
3. **大量防御在防项目自己的代码。**
   - 调试用 CST oracle 与契约代码约 9,000 行，占 core 的 24.5%；生产路径上另有 `layout/invariants.ts` 等契约文件。
   - 生产路径上对自建对象做 Proxy 检测和来源证明，约占 20% 的 CPU。
   - 加入 INSERT INTO 与 SET 的那次提交（`4b73934`），53% 的新增代码落在 oracle 里。
   - v2 以来 33 个 fix 提交中，约 13 个修的是发布、构建、证据机制本身，只有约 10 个修的是用户可见的排版。

所以本次重构**不换骨架，换重心**。具体做法：

- 先建立排版规格（黄金快照）；
- 再删除只防自己的兜底；
- 然后在"完整建模"和"原样保留"之间补一层通用排版；
- 最后对照快照修排版缺陷。

## 2. 目标、非目标与完成标准

### 2.1 目标

1. **排版正确优先**：`tests/golden` 是排版行为的唯一规格。
2. **删除只防项目自身代码的兜底**，包括 provenance、brand、WeakSet 归属、对内部对象做 Proxy/descriptor 快照、debug oracle、记账型预算、只给测试用的统计。
3. **未建模语法尽量格式化**：新增通用排版层，不再一律"原样加 warning"。
4. **工程从简**：一条构建、一条测试、一条打包命令；`npm test` 结果确定且速度快。

### 2.2 非目标

- 可证明正确；对抗恶意输入、hostile 对象或项目内部 bug。
- npm 公共 API、Marketplace 发布、发布产物的字节级溯源。
- 墙钟或比值型性能门。
- 多方言 parity（取决于 D1）。
- 扩大 Experimental DDL 子集（3.0 之后另议，见附录 C 的 K19）。

## 4. 3.0 安全底线（只有这五条，必须守住）

1. **lexer 无损**：所有 leaf 拼接起来必须等于原文。只在 lexer 里检查一次。
2. **格式化输出的 token 等价与粘连保持**。适用于 `formatSql` 与 `formatHiveDdl`；Extract 是生成式操作，不适用（见 §5.5）。
   - 重新 lex 输出，非空白 token 序列必须与原文一致：kind、channel、原文都相同，只有计划中做大小写转换的关键字按大小写不敏感比较。
   - **粘连保持**分两部分。检查对象是按顺序排列的非空白 leaf，包括 channel 为 `protected` 的 parameter，不能只看 channel 为 `code` 的 leaf；注释算作分隔，不和两侧配对。
     - **单词类相邻**：相邻两个 leaf 如果都属于单词类（keyword、identifier、number、parameter），它们之间有没有空白必须与原文相同。原来零宽的不能插入空白，原来有空白的不能删成零宽。
     - **模板片段**：从每个 `${…}` 出发，向两侧吸收零宽相邻的 leaf，遇到空白、换行、注释或 `,`、`(`、`)`、`;` 时停止，得到一个模板片段。片段内部不得出现空白；片段与片段外紧邻 leaf 之间原有的空白也不得删除（实测种子上 0 条）。`?`、`:name` 这类绑定占位符不做文本替换，不适用这一条。
     - **前提是 D13 的展开约定**：展开值不改变词法结构。在这个前提下，`,`、`(`、`)`、`;` 两侧仍是 SQL code。Hive 中又没有以这四个符号开头或结尾的多字符 token，所以在它们旁边加空白，不会改变替换后的分词。约定之外的展开（第三轮复核 T1：两个变量拼出一个字符串）不在保护范围内。
   - **实现方式**（P1b）：Hive lexer 把每个模板片段合成一个 channel 为 `protected` 的 parameter leaf，所以片段内部不出现空白、不改大小写由 token 等价逐 leaf 保证，运行时的粘连检查只剩单词类相邻和片段外侧空白两条。删掉片段旁的空白后，片段在重新 lex 时会吞掉邻居，表现为 token 不等价，这种情况同样按粘连违例处理。golden runner 仍按上面的完整定义独立检查。
   - 任一项不成立时，整个 target 返回原文并给出诊断：token 不等价是 `failed` 加 `FMT_TOKEN_EQUIVALENCE`（视为内部错误）；粘连违例是 `preserved` 加 warning `FMT_GLUE_PRESERVED`。
   - token 等价不等于语义等价。粘连保持专门补上本项目 lexer 与 Hive 文本替换、Hive 词法不一致的盲区。下面这些改动的 token 指纹都不变：
     - `0L`→`0 L`；
     - `${p}desc`→`${p} DESC`；
     - `${a}${b}`→`${a} ${b}`；
     - `${v}and`→`${v} AND`；
     - `${lhs}=1`→`${lhs} = 1`：当 `lhs` 为 `x>` 时，`>=` 会变成 `>` 和 `=`。
   - 实测（1,106 条 formatSql 种子的当前输出）：单词类规则违例 0 条；模板片段规则违例 2 条，都是 `${hiveconf:…}` 紧贴运算符（`ds=${hiveconf:run_date}`、`${hiveconf:value}+1`）。另外，K7 类输入都能被检出。
   - 代价：模板紧贴运算符的写法，今后保持原样，例如 `ds=${hiveconf:run_date}` 不再被加上空格。写成 `ds = ${hiveconf:run_date}` 或 `ds='${hiveconf:run_date}'` 的照常排版。
3. **编辑原子提交**：
   - 计算前快照文档版本；
   - 计算出全部 target 的结果；
   - 提交前复查文档身份和版本；
   - 用一次 `editor.edit` 提交，并检查其返回值。
   - 任一 target 失败、取消或过期时，不提交任何 edit。
4. **资源上限**：
   - 输入不超过 524,288 个 UTF-16 code units；
   - parser 嵌套深度 256，外加 parser trial 预算和 `MAX_UNSUPPORTED_CLAUSE_PROOFS`；
   - **输出上限分两步走。**
     - P6 之前：沿用现有 layout 数值预算。只拆掉证明和记账外壳，阈值和检查点都不变，所以行为不变。
     - P6 第 1 步：换成**生成期**上限。renderer 边写边计数，超限立即停止，而不是先拼出整串、重新 lex 之后才发现超限。
     - `formatSql`：每个 target 的输出 ≤ 4 × 输入 + 64 Ki。
     - `formatHiveDdl` 与 Extract：沿用现有的 `ddlOutputWithinBudget`（4 × 输入 + 4,096 + 160 × 行数）。Extract 的输出天然是输入的 5 倍左右，不能套用 formatSql 的公式。
   - 批量操作不另设总上限：targets 互不重叠，总量已由单 target 上限和输入上限约束。
   - 超限一律返回原文。
5. **受保护文本不改写**：下列内容的字符保持原样，包括大小写和内部空白。
   - 字符串、注释、引号标识符、`${…}` 模板；
   - Hive 数字 literal 整体：`0L`、`10Y`、`5S`、`1.0D`、`1.0BD`；
   - 脚本命令载荷：命令头之后的路径、URI、类名、配置值、shell 参数（列表见 §5.3），包括现有 `SET` 的值；
   - 模板片段（定义见第 2 条），例如 `db_${env}`、`${p}desc`、`ds=${hiveconf:run_date}`。片段内部不插空白，也不改大小写；片段作为一个原子参与排版。保护范围以 D13 的展开约定为前提。
   - 通用层中，语句头表（§5.3）以外的词：保持原大小写。

**原样保留的单位**是最小安全片段：一个模板片段、一段载荷或一个 opaque 节点。只有以下情况才让整个 target 保持原文：
- 词法错误（未闭合的字符串或注释）；
- 资源超限；
- 第 2 条校验失败；
- 内部异常；
- 用户选择了 `bail_out` 策略，且还有原样片段（D6）。

除此之外不再有运行时"契约"。

- **内部 bug 的处理**：直接 `throw`，由顶层 catch 返回原文加 `FMT_INTERNAL`，诊断里附上异常消息。这是唯一需要的 fail-closed。
- **幂等**：作为测试属性，由 golden runner 自动检查，不做运行时检查。

### 5.2 管线

```
lex → parse(CST) → analyze(index + trivia) → plan → compile(Layout IR) → render
    → [有对齐目标：把 plan 中对应 gap 改写为 pad-to-column → compile → render]
    → token 等价 + 粘连保持 → FormatResult

- **去掉的检查**：各阶段之间不再做 canonical/provenance 证明，形状由 TypeScript 类型保证。
- **保留的检查**：少量廉价的语义断言，例如 plan 的 scope 嵌套/冲突检查（`plan.ts:896-975`）、leaf 连续性与 root 覆盖、renderer 的 newline 边界契约（`render.ts:606-626`）。断言失败直接 `throw`。

### 5.3 三层排版与命令载荷

| 层 | 适用范围 | 行为 |
| --- | --- | --- |
| 已建模 | registry 中 `formatted` 的能力；P6 新建模的小构造与 CTAS | 完整 layout |
| **通用（新增）** | 语句级 opaque 中属于 SQL 语法的部分（`use`、`msck`、`analyze`、`show`、`describe`、`load data`、`create function` 等），以及 `structured` 能力 | **只改空白的量，不改空白的有无**：<br>• 同一行内的连续空白压成一个空格，删除行尾空白（字符串、注释和载荷内部的不动）；<br>• 原有换行和续行缩进保留；<br>• 零宽间隙不插空白，已有的分隔不删除；<br>• 只对语句头表命中的前导关键字应用大小写，其余词保持原样；<br>• 不报 warning |
| **命令载荷（新增）** | `add`、`list`、`delete` 后接 `jar(s)`、`file(s)`、`archive(s)`；`dfs`、`!`、`source`、`reset`、`compile`；`set`（沿用现有 set-payload 节点）。范围是命令头之后、语句结尾 `;` 之前的全部文本 | 命令头按语句头表应用大小写；载荷原样，大小写和内部空白都不动 |
| 原样保留 | 未闭合字符串/注释、定界符不平衡、超出资源上限、第 2 条底线失败、无法建模的模板片段 | 原文；给出诊断。范围按 §4 取最小安全片段 |

- **通用层为什么不改空白的有无**：R1、R2 的反例（`0 L`、`/ tmp / my - udf.jar`）都是往零宽间隙里插入空白造成的。只改空白的量，从构造上排除了这一类问题，第 2 条底线的粘连规则在通用层也自动成立。代价是通用层不会把 `a=b` 改成 `a = b`；这类语句以命令为主，可以接受。
- **keyword 大小写只用语句头表**（S2）：lexer 的 keyword 分类不能证明一个词在这里是语法。例如 `show role grant user string` 中，`show role grant user` 被 lex 成 identifier，只有用户名 `string` 是 keyword；而 Hive 的 principal 名区分大小写。所以通用层不按 lexer 分类改大小写，只把语句开头命中下表的那段前导关键字转换大小写，其余词一律保持原样。
  - 匹配规则：只在真实的语句起点匹配；按完整 token 序列比较，不按字符前缀；只匹配 channel 为 `code` 的 identifier 或 keyword leaf，不处理 quoted-identifier、字符串和模板。命中的 leaf 在 CST 中标为允许转换大小写的语法角色；token 等价检查只对计划转换的 leaf 忽略大小写，不重新放开"所有 keyword 或 identifier 都可转"。
  - 初始语句头表（不区分大小写，取最长匹配）：`USE`；`SHOW DATABASES|SCHEMAS|TABLES|VIEWS|PARTITIONS|FUNCTIONS|COLUMNS|TBLPROPERTIES|CREATE TABLE`；`DESCRIBE|DESC [FORMATTED|EXTENDED] [DATABASE|FUNCTION]`；`MSCK [REPAIR] TABLE`；`ANALYZE TABLE`；`LOAD DATA [LOCAL] INPATH`；`TRUNCATE TABLE`；`DROP TABLE|VIEW|FUNCTION|DATABASE [IF EXISTS]`；`CREATE [TEMPORARY] FUNCTION`；`ALTER TABLE`；以及命令载荷层的命令头（`ADD JAR` 等）。
  - 授权类语句（`GRANT`、`REVOKE`、`SHOW ROLE GRANT`、`SHOW GRANT`、`CREATE ROLE`、`DROP ROLE`）不进表，整句保持原大小写，只做空白的量的规范化。
  - 表是数据，后续按需要追加；每加一项都要加 golden 用例。
  - 效果示例：`analyze table t compute statistics` 输出 `ANALYZE TABLE t compute statistics`。头之后的关键字不转换，这是有意的取舍。
- **K10 的小构造不靠通用层**：`div`、`nulls last`、`limit … offset` 等出现在已建模查询的内部，要得到完整排版，就要在 parser 中建模（P6 第 4 步）。
- **CTAS 走已建模层**（R7）：通用层不会产生 query 节点，所以 CTAS 需要在 parser 中划出"外壳"与"查询"的真实边界（P6 第 5 步）。

接入点（基线行号）：

- `layout/verbatim-claims.ts:102-188`：verbatim claim 的生成处，是通用层的主接入点；其中 `set-payload` 分支（`:103`）是命令载荷层的现成样板。
- `layout/query-layout-context.ts:103-139`：authority 计算。
- `layout/plan.ts:513-528`：`formattedAuthority` 门。
- `syntax/statement-parser.ts:290-342`：INSERT 的"语句头 + 查询"入口；CTAS 参照它实现。

可选：增加 `-- sqlbeautify: off` / `-- sqlbeautify: on` 注释，作为所有者手动跳过某段 SQL 的出口。**P6 不做**（所有者 2026-10-24 决定）：没有复现的需求，底线已保证 token 安全，需要跳过时可以只格式化选区。要做的话，opaque 节点必须带一条精确匹配的诊断（structural-index 的检查），还需要新的诊断码、`bail_out` 的豁免和宿主的诊断过滤。

### 5.4 适配层

- **计算**：`computeEdits({op: "format" | "hive-ddl" | "extract", source, targets, options, newline, tabSize})`，是纯函数，direct 和 worker 都能运行。流程：
  1. 规范化 targets（排序、去重叠），只做一次；
  2. 用共享的范围校验检查每个 target；
  3. 逐个 target 执行；
  4. 返回统一结构 `{status, edits[{start, end, text, sourceMap?}], diagnostics}`。

  `formatHiveDdl` 的结果在这里统一经过第 2 条底线的检查，与 formatSql 共用同一个检查函数。Extract 不做 token 等价检查。
- **范围校验**（S6）：
  - **共用的只有底层工具**：offset 换算、`isLineStart`/`isLineEnd`、"两端不能落在 protected leaf 或注释内部"。
  - **语法完整性按 op 各自判断**：查询要求选区对应完整的 statement、clause 或 list 节点；DDL 与 Extract 由各自的 parser 判断能否完整消费。CREATE 在查询 analysis 中是 opaque，不能套用查询的归属门。
  - **P4a 保留各 op 现有的边界策略**，包括 DDL 的行边界规则，行为不变；P4b 第 1 步再把 DDL 的行尾规则换成共享的 `isLineEnd`，从而关闭 K18（`589b027`）。
- **宿主提交**：只有一个提交函数，按 §4 第 3 条执行。选区映射：edit 带 source map 就走 source map，没有就走 delta 映射。
- **执行器**（D4 选 A）：
  - 输入 ≥ 32 Ki code units 时才走 worker；
  - worker 懒创建，用 `Map<id, {resolve, reject}>` 跟踪请求；
  - worker 出现 error 或 exit 时，reject 全部挂起请求，下次请求自动重建；
  - 取消请求时直接 `terminate()`，重建约需 85 ms。
- **诊断**：一个 `DiagnosticCollection` 加一个 `pending: Map<uri, {version, output, diags}>`。
  - 有 edits 时，提交成功且文档文本等于预测输出才发布；
  - 文档发生无关编辑或关闭时清除；
  - `onDidChangeConfiguration` 时刷新 `CFG_*` 诊断。

**目录布局：**

```

- **文件扩展名**：用 `.txt`，避免被 VS Code 当作 SQL 打开。否则 formatOnSave（也就是本扩展）会改写快照。
- **选项头**：输入首行可写 `-- golden: {...}`。runner 只精确剥掉这一行及其后的 `\n`，所以 BOM 和 CRLF 正文不受影响。字段：
  - `op`：`formatSql`、`formatHiveDdl` 或 `extractDdl`；
  - `options`：格式化选项；
  - 执行环境：`mode`（document、statement 或 fragment）、`newline`（`\n`、`\r\n` 或 `\r`）、`tabSize`、`startColumn`（DDL 和 Extract 的续行起始列）。缺省时与适配层的实际行为一致：mode 为 document，tabSize 为 4，startColumn 为 0；newline 缺省时按适配层对文档 EOL 的实际推断，不一律当作 LF。重采时区分"显式指定"与"缺省"，以免 CRLF 种子在采集时失真。
  - `variants`：`{"<variant>": {…}}`，可以覆盖上面任意字段。每个 variant 有自己的输出文件 `<name>.<variant>.out.txt` 和快照键 `<group>/<name>#<variant>`。

**实施记录（2026-10-22）：**

- **入口与命令**：
  - runner 是 `tests/golden/run.js`，共 685 行，比"约 150 行"的估计多，多出来的是 DDL 事务、`--private`、`--fuzz`、大小写授权，以及粘连和大小写自检。
  - `npm run test:golden` 已作为 `golden` suite 接入 `test:verify`，CI 从 P1 起就检查 golden；`npm run golden:update` 用于重写快照。
- **调用方式**：
  - formatSql 调用 `executeFormatSql(source, options, mode, newline, false, tabSize)`，与 executor 的参数相同；newline 缺省时按 `inferRenderNewline(source, "\n")` 推断，与适配层一致。
  - DDL 与 Extract 调用 `runExperimentalDdlTransaction`。快照中的文本是 normalize 之后的最终 replacement；status 和 codes 是 op 自己的结果。只有适配层丢弃了一个可编辑的结果时，才追加适配层的 code；目前没有这种用例。
  - `startColumn: N` 表示目标前面有 N 个空格的外部缩进，适配层据此算出续行起始列。快照中续行已带上这 N 个空格，首行没有。外部缩进含 tab 的情形（`\t(` 与 `    (`）不在这个模型内，由 P4a 的 unit 覆盖（D.3 的 wave4d-transaction 行）。
  - 事务在调用 op 之前就拒绝的目标（例如词法错误），runner 直接调用 op 取 status。
- **token 比对**：kind、channel、原文都要相同。只有该操作计划改大小写的 leaf，才允许整体改成大写或小写（P1-R1 修复，原来对所有 keyword 和 code channel 的 identifier 都放开）：
  - formatSql：layout plan 计划改大小写（`leafEmissions` 为 `keyword-case`），并且 analysis 中 `keywordCaseEligible` 为真、语法角色是 `syntax-keyword`、`word-operator-keyword`、`builtin-type-keyword` 之一的 leaf。这与 runtime 的 token 等价检查（`format.ts`）同一口径。`rlike`、`varchar` 被 lex 成 identifier，但在 CST 中是关键字角色，所以允许；PostgreSQL `a::int` 中的 `int` 有类型关键字角色，但 plan 不改写它，所以不允许。
  - formatHiveDdl：先用 DDL formatter 判断输入是否属于已建模子集（`CREATE TABLE` 加列清单、`PARTITIONED BY`、`STORED AS`）。不属于时一律不授权，例如 CHECK 约束、`location` 等未建模后缀。属于时，用 formatter 自己的 parser 调用（`parseSqlArtifact`、`splitTopLevelTypeItems`、`parseTypePrefixFromArtifact`）读出结构，只放行：
    - 语句头关键字，`PARTITIONED BY`、`STORED AS` 和其后的存储格式，按语法顺序定位；
    - 每个列的类型节点中，带 `type:name` marker 且 `keywordCaseEligible` 的类型名，递归进入嵌套类型；圆括号里的标量参数（`decimal(int)` 的 `int`）不放行；
    - 类型结束后紧跟的列 `COMMENT` 关键字；名为 `comment` 的用户类型不放行。
    - 只考虑 code channel 的 keyword、identifier leaf，所以注释、字符串、引号标识符都不会被放行；表名、列名、struct 字段名也保持原样。
    - 历次收紧：第二轮复核前，depth 0 的任何 leaf 都放行；第三轮复核前，CHECK 表达式中的比较符会被当作类型括号计数；第四轮复核前，类型位置按单词表放行，标量参数和名为 `comment` 的用户类型因此被误放行。
  - `tests/golden/tools/check-case.js` 把两种授权和 formatter 的实际行为对照：同一输入分别用 `keywordCase` upper 和 lower 格式化，两次输出不同的 leaf 就是 formatter 实际改大小写的 leaf。两者完全一致，即没有漏放行，也没有多放行：
    - golden 中 1,735 个 formatSql 输入和 148 个已建模 DDL 输入；
    - 7 个针对性 formatSql 输入（PostgreSQL 的 `::` 转换、cast、`rlike`、命令载荷、授权语句、模板）；
    - 3,168 个生成的 DDL 输入：22 种类型形态（含标量参数、名为 `comment`、`orc` 的用户类型、嵌套 map/array/struct）× 6 种列名 × 4 种后缀 × 3 种表头 × 有无列 COMMENT。同一网格在第四轮复核前的版本上报出 1,800 个多放行。
    - K29 的 1 个输入因为输出改变了 token 数，不参与逐 leaf 对照。
  - 模板片段内的 leaf 即使被授权，也不允许改大小写，按粘连违例报告（§4 第 5 条）。
  - P3 的通用层引入语句头表之后，这里同步加入语句头表的授权。
- **runner 自身的检查**：
  - 启动时先跑粘连自检：`${v}+ 1` 必须报 1 次违例，`select ${v}, x` 必须报 0 次，等等。

### P1b 底线补强（行为变化，范围很小）

在删除任何机制之前，先让 §4 第 2、5 条真正成立（R6）。

1. **粘连检查**：在 `format.ts:318-395` 的 token 等价函数中加入 §4 第 2 条的两部分粘连检查，单独一个提交。K7 类用例和两条 `${hiveconf:…}` 种子会从"被错误地格式化"变成"返回原文加诊断"，同时删除它们的 `glue` 豁免。
2. **Hive 模板词法**（K28）：在 Hive profile 下，`${` 总是开始一个 parameter，即使它紧跟在标识符字符之后。现在 Hive 使用的 `ASCII_IDENTIFIER_CHARACTERS`（`lexical-profile.ts:350-357`）允许 `$` 作为标识符的后续字符，于是 `tbl_${dt}` 被 lex 成 `tbl_$`、`{`、`dt`、`}`，模板保护在这里失效。这一步放在第 3 步之前，以免在旧的错误词法上设计原子。同一步从 Hive profile 的 `HIVE_OPERATORS` 中删除 `<<` 和 `>>`（K29）：HiveLexer 中只有 `<`、`>`，没有这两个多字符 token。
3. **模板片段成为原子**：模板片段（§4 第 2 条）成为一个原子。原写由 parser 完成，实施时改在 lexer（见下面的实施记录）。
   - 出现在标识符位置时，作为普通的名字参与排版；在其他位置作为 verbatim 片段。
   - 原子内部不插空白，也不改大小写。
   - 效果：K7 的 `order by ${p}desc` 输出 `ORDER BY\n      ${p}desc`，而不是整句退回原文。

5. **CTAS**（R7，关闭 K12）：
   - **parser**（S3）：在 `statement-parser.ts` 中，对 `CREATE [TEMPORARY] [TRANSACTIONAL] [EXTERNAL] TABLE` 或 `CREATE MANAGED TABLE` 开头的语句，从左往右找**第一个**满足以下条件的 `AS`，作为外壳的终点：
     - 括号深度为 0；
     - 前一个 code token 不是 `STORED` 或 `DEFINED`；
     - 后一个 code token 是 `SELECT`、`WITH` 或 `(`。Hive 还允许 `VALUES`、`MAP`、`REDUCE` 开头，本项目的 query parser 不支持这几种，遇到时整句保留。

     找到后立即停止扫描，`AS` 之后的全部内容交给 `parseQueryRange`；查询内部的 `AS`（例如 CTE 的 `q AS (`）不再参与判断。查询不能被完整消费时，整句仍按现在的方式保留。
     - 判断基于 lexer token 和括号深度。字符串和注释里的同名词天然被排除，不用正则。
     - 为什么"第一个"就是外壳终点：按 Hive `rel/release-4.0.1` 的 `CreateDDLParser.g`，外壳之后紧跟 `KW_AS selectStatementWithCTE`。对外壳规则做闭包，可达的 `AS` 中，不在括号内的只有两类：
       - `STORED AS …`（文件格式子句，含 `STORED AS INPUTFORMAT`；skewed 子句中还有 `STORED AS DIRECTORIES`），被"前一个 token"条件排除；
       - `NULL DEFINED AS '…'`，后面必须是字符串，被"后一个 token"条件排除；同时把 `DEFINED` 也列入"前一个 token"的排除项，这样 `null defined as (select 1)` 这类 malformed 外壳不会被误认成 CTAS（第三轮复核的 Question）。

       cast、窗口、子查询等其他 `AS` 只出现在列定义或分区规格的括号内。
     - FROM 开头的写法不属于 `selectStatementWithCTE`，不是合法的 CTAS，按原样保留。
     - 外壳本身不做完整的语法校验：外壳只走通用层，只改空白的量，保留外壳的非空白 token 和受保护片段。这里不声明外壳语法合法。
     - **表名边界**（第四轮复核）：`STORED`、`DEFINED` 在 Hive 中是 nonReserved 词，可以作表名，例如 `create table defined as select 1`、`create table db.defined as select 1`、`create table stored as select 1`。所以这两项排除只在相应外壳子句的语法位置生效：先确认表名（`identifier` 或 `db.identifier`）的边界，表名之后紧跟的 `AS` 直接作为外壳终点。不需要实现完整的 DDL 校验器。
   - **CST**：新增 CTAS 语句节点。`AS` 之前是外壳，按通用层排版；之后交给现有的 `parseQueryRange`。
   - **layout**：外壳按通用层输出，`AS` 留在外壳末行，查询从下一行开始按普通查询排版。
   - **golden**：外壳带 `COMMENT`、`STORED AS`、`ROW FORMAT DELIMITED … NULL DEFINED AS '\\N'`、`TBLPROPERTIES`、`IF NOT EXISTS`、`TEMPORARY`；字符串和注释里出现 `as select`；顶层带 CTE：`create table t as with q as (select a from src) select a from q`；以 nonReserved 词作表名的上述三句；malformed 外壳 `create table t row format delimited null defined as (select 1)`（应保留原文）。

## 8. 复核协议（GPT）

**复核时机**：P0 之前复核本方案；之后每个阶段在合入 `main` 之前各复核一次。

**输入**：本文、阶段 diff（`git diff main...claude/sleepy-allen-pa7396`）、`npm test` 输出、golden 变化清单（runner 输出）。

**检查项：**

1. 阶段范围是否与本文一致，有无夹带改动；
2. 重构阶段 golden 是否零变化；行为阶段每个变化是否有解释；
3. §4 的五条底线是否仍然成立；
4. 有没有重新引入"明确不做"中的机制；
5. 新代码是否可读，是否让总代码量下降。

**严重度（个人使用口径）：**

- **Blocker**：违反 §4 任一条且附有复现，或重构阶段出现未解释的 golden 变化。
- **Major**：常见 Hive SQL 出现排版回归或幂等失败（附复现）；阶段明显偏离本方案。
- **Minor**：可读性、命名、残留死代码、注释不准确。
- **Question**：没有复现的疑虑，作为问题提出，不计为缺陷。

**不在复核范围（请不要提出）：**

- hostile、Proxy、accessor、prototype 污染类输入，以及恶意 workspace 配置；
- 内部对象的 provenance、brand、所有权证明；
- 没有复现的理论竞态；
- 缺少性能门或发布字节溯源；
- 缺少 npm API 或类型声明；
- "与 2.x 技术契约不一致"本身。

**每条发现必须包含**：位置（`file:line`）、复现（SQL + 选项 + 实际输出 + 期望输出，或者具体的调用路径）、修改建议。

**处理规则**：
- Blocker 和 Major 在合并前必须解决，或由所有者明确豁免；
- Minor 可以延后处理；

## 定位

SQL Beautify 是所有者个人使用的 Hive SQL 格式化 VS Code 扩展，VSIX 通过 GitHub Releases 分发，

5. 字符串、注释、引号标识符、`${…}` 模板、Hive 数字 literal、脚本命令载荷、模板片段，

## 排版规则

- `tests/golden` 是排版行为的唯一规格。任何排版变化都必须体现为 golden diff，并在提交说明中解释。
- 修排版 bug：先加或改 golden 用例，再改 layout policy。
- 纯重构提交：golden 必须零变化。
- layout policy 只产出 Layout IR；renderer 是唯一写空白和关键字大小写的地方；render 之后不做全局正则。
- 未建模结构优先走通用排版层；只有词法不安全时才原样保留，且只保留最小安全片段。
- 通用排版层只改空白的量，不改空白的有无；只对语句头表中的前导关键字改大小写；命令载荷原样保留。
- 结构判断来自 CST，不按单词值或局部正则猜测语法。

## 附录 B：package.json scripts 与 CI（P2 已落地）

```json
"scripts": {
    "build": "node scripts/build.js",
    "vscode:prepublish": "npm run build",
    "typecheck": "tsc -p tsconfig.json --noEmit",
    "test": "npm run build && node tests/run.js",
    "golden:update": "node tests/golden/run.js --update",
    "test:private": "node tests/golden/run.js --private",
    "test:vscode": "npm run build && node scripts/run-vscode-smoke.js",
    "package": "vsce package --no-dependencies -o vscode-sql-beautify-v$npm_package_version.vsix && node scripts/check-vsix.js"
}
```

- `package` 只负责打包和检查文件清单，不再串 typecheck 和 test。
- `vsce package` 会自动执行 `vscode:prepublish`，也就是再 build 一次。esbuild 构建约 0.2 s，这次重复可以接受。
- golden runner 自己从 src 打包要用的 core，所以 `golden:update` 和 `test:private` 不前置 build（草案原来写了）。`test:private` 用法：`npm run test:private -- <目录>`。

CI（`.github/workflows/build-vsix.yml`，80 行）：

- `check` job：
  - 在 push 到 `main` 或 `claude/**` 时触发，并保留 pull_request 触发；使用 Node 22。不走 PR 之后，功能分支的推送也要跑 CI，合入 `main` 前就能看到结果；
  - 依次执行 `npm ci`、`npm run typecheck`、`npm test`、`npm run package`，各执行一次；
  - 上传 VSIX。
- `release` job：
  - 只在 `main` 上手动触发，且 `check` 通过；
  - 版本号取自 `package.json`，tag 约定为字符串 `v<version>`；
  - CHANGELOG.md 必须有 `### <version>` 标题；
  - 用 `git ls-remote --tags origin refs/tags/v<version>` 确认该 tag 尚不存在，查询失败时 job 失败；
  - 执行 `gh release create v<version> <vsix> --target <workflow checkout 的 SHA>`，不使用 `--clobber`。
- `vscode-smoke`：手动触发并勾选输入时运行，只测 stable。

```js
// 对每条 formatSql 结果：lex 原文与输出，按顺序比较非空白 token；
// 相邻两个 token 都属于单词类、且两边"前面有没有空白"不一致时，记为一次违例。
var f = require("./dist/sql-formatter.cjs");
var WORD = { keyword: 1, identifier: 1, number: 1, parameter: 1 };
function code(leaves) {
    var out = [], gap = true;
    leaves.forEach(function (l) {
        if (l.kind === "whitespace" || l.kind === "newline") { gap = true; return; }
        out.push({ kind: l.kind, raw: l.raw, gap: gap });
        gap = false;
    });
    return out;
}
function glueViolations(source, output, dialect) {
    var a = code(f.lexSql(source, { dialect: dialect }).leaves);
    var b = code(f.lexSql(output, { dialect: dialect }).leaves);
    var count = 0;
    for (var i = 1; i < a.length && i < b.length; i++) {
        if (WORD[a[i - 1].kind] && WORD[a[i].kind] && a[i].gap !== b[i].gap) {
            count += 1;
        }
    }
    return count;
}
// 模板片段规则：从每个 ${…} 向两侧吸收零宽相邻的 leaf，遇到注释或 , ( ) ; 停止；
// 片段内部的间隙在输出中出现空白，记为一次违例。a、b 为上面 code() 的结果，需额外记录 raw。
var STOP = { ",": 1, "(": 1, ")": 1, ";": 1 };
function absorbable(t) {
    return t.kind !== "line-comment" && t.kind !== "block-comment" &&
        !(t.kind === "punctuation" && STOP[t.raw]);
}
function fragmentViolations(a, b) {
    var inside = [], count = 0, i, j;
    for (i = 0; i < a.length; i++) {
        if (a[i].kind !== "parameter" || a[i].raw.slice(0, 2) !== "${") continue;
        for (j = i + 1; j < a.length && !a[j].gap && absorbable(a[j]); j++) inside[j] = true;
        for (j = i; j > 0 && !a[j].gap && absorbable(a[j - 1]); j--) inside[j] = true;
    }
    for (i = 1; i < a.length && i < b.length; i++) {
        if (inside[i] && b[i].gap) count += 1;
    }
    return count;
}
```

- 第一个函数是单词类规则，第二个是模板片段规则（S1）；1,106 条 formatSql 种子上分别为 0 条和 2 条违例。第三轮复核用原样提取的脚本复现了这两个数字。
