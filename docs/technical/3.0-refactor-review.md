## 1. 必须修订的发现

### R1 / Major：现有 token 等价挡不住 Hive 数字后缀被拆开

**位置：** 方案 `:99`、`:158`、`:332`；代码 `src/core/lexer/lossless-lexer.ts:636`。

**复现，默认 Hive、upper：**

```sql
select 0L from t
```

当前输出保留 `0L`，带 `SYN_UNEXPECTED_TOKEN`。现有 lexer 将它拆成 `number("0")` 和 `identifier("L")`。候选通用输出 `SELECT 0 L FROM t` 与原文的非空白 token 指纹完全相同；`10Y → 10 Y`、`1.0BD → 1.0 BD` 同样如此。Hive 自己的 lexer 将带后缀数字识别为一个 literal；加空格后会变为数字加别名，改变类型或解析结果。

**期望：** 可以改外部排版，但必须保留 `0L`、`10Y`、`1.0BD` 的原子性。不能把 token 等价称作语义等价。

**修改建议：** 在通用层上线前补齐 Hive 数字 literal 的词法单元，覆盖 `L/S/Y/D/BD`，并评估 Hive 允许的数字开头标识符。更小的过渡方案是保留尚未正确建模的相邻词法片段。为 literal 与别名的对照组建立 golden；更新第 5 条底线，包含方言 literal，而非仅引号文本。

**证据边界：** 上述 token 指纹是本机实测；Hive 对 literal 的解释依据 [Apache Hive lexer](https://github.com/apache/hive/blob/master/parser/src/java/org/apache/hadoop/hive/ql/parse/HiveLexerParent.g)。本机没有运行 Hive 服务。候选输出用于证明检查盲区，不代表尚未实现的通用层已经输出这些文本。

### R2 / Major：脚本命令载荷不能按 SQL token 空格和 keyword 大小写处理

**位置：** 方案 `:99`、`:111`、`:158`、`:163`；代码 `src/core/layout/verbatim-claims.ts:103` 的 `set-payload` 分支。

**复现，默认 Hive、upper：**

```sql
add jar /tmp/current.jar;
add jar /tmp/my-udf.jar;
```

当前均保持完整原文。lexer 把第一个路径内的 `current` 当作 keyword；候选输出 `ADD jar /tmp/CURRENT.jar;` 通过方案规定的 keyword 不区分大小写指纹，但在大小写敏感文件系统上指向另一个文件。第二个候选输出 `ADD jar / tmp / my - udf.jar;` 也通过指纹，但 Hive `AddResourceProcessor` 会按空白拆成多个资源参数。

**期望：** `ADD JAR` 头部可规范化；路径及资源参数内容与内部空格原样保留。同样不能取消现有 `SET` payload 的保护，再把配置值当 SQL 表达式排版。

**修改建议：** 在三层排版表中明确区分「语法」和「命令载荷」。保留或复用有界 payload 节点；只转换已确认属于语法的 keyword，不能只凭 `leaf.kind === "keyword"`。第 5 条加入脚本命令载荷。对 ADD JAR、SET 的路径、URI、keyword 同名文件及多个参数加 golden。

**证据边界：** 指纹在本机实测；空白分词依据 [Apache Hive AddResourceProcessor](https://github.com/apache/hive/blob/master/ql/src/java/org/apache/hadoop/hive/ql/processors/AddResourceProcessor.java)。没有运行 Hive 资源加载。

### R3 / Major：golden 的通用断言不适用于 Extract，迁移格式也漏掉实际环境参数

**位置：** 方案 `:190–203`、`:239–254`、`:605–607`。

**复现一，默认 Extract：**

```sql
SELECT a FROM t
```

实际结果是 `status: extracted`、`text: "     a __TYPE_REQUIRED__\n"`。输出必然与 SELECT 输入 token 不等价；把输出再次交给 Extract 则为 `unsupported`。§5.5 却要求每个 golden 检查 token 等价和幂等；按通用格式化成功状态判断会拒绝正常 Extract。

**复现二，同一 SQL、不同正常编辑器 tabSize：**

```sql
select `a\tb` as x,
       `abcdef` as y
from t
```

此处 `\t` 表示输入中的实际制表符。内部 formatter 的 tabSize 2、4、8 分别产生三个不同且正确的对齐输出。现有种子只有 `origin/op/options/source`，没有 `mode/newline/tabSize/startColumn`；种子中唯一 `options.tabSize: 8` 是一个非法公共 DDL 选项测试，不是渲染环境覆盖。原测试中的这些路径不能只靠调用公共二参数 facade 迁入 golden。

**期望：** 正常 Extract 能通过 runner；原有 fragment/EOL/tabSize 行为在删旧测试前有等价的测试入口。

**修改建议：**

- 以 `op` 分配性质检查：formatSql / formatHiveDdl 检查 token 保真和文本幂等；Extract 检查重复相同输入结果一致、列名/顺序与生成 literal 正确、失败保留原文，不做输入输出 token 等价。
- 第 4 条底线中注明 token 等价适用于格式化，不适用于生成式 Extract。DDL newline 重构可删输出规范化用的重新 lex，仍需明确最终格式化 token 检查放在哪里。
- golden 元数据增加内部执行环境或明确迁至 unit 的清单，至少包含 `mode/newline/tabSize/startColumn`；variants 必须有各自的输入参数及输出文件命名契约。
- 删除旧测试的前提应是相同行为和参数已经被新 runner 覆盖，不能仅以 SQL 输入已采集作依据。

### R4 / Major：P3 第 4、5 步先删证明生产方，与第 6 步的顺序冲突

**位置：** 方案 `:291–295`、`:607`。

**具体调用路径：** `formatSql → compileLayoutPlan → createLayoutArtifact → render → measureLayoutArtifact`。

`layout/artifact.ts:133` 调用 `validateLayoutDoc`，并把预算写入 artifact proof 表；`renderer/metrics.ts:164–193`、`renderer/render.ts:178` 仍读这张表。doc-factory 的 proof 则被工厂自己的 `belongsToFactory`、layout invariant 和 metrics 读取。P3 第 4 步先删 invariant 与 artifact 证明表，第 5 步再删工厂证明，第 6 步才改消费方：它们不能按所写顺序各自保持可用。

本机临时 bundle 实验仅取消 artifact proof 写入，`select a from t` 即返回 `failed / RENDER_ARTIFACT_PROVENANCE`；仅取消 doc-factory proof 写入，则返回 `failed / LAYOUT_COMPILE_DOC`。这是依赖顺序证据，不是反对删除机制。

另有测试入口依赖：P3 第 2 步删除 `core/index.ts` 和 `analysis/index.ts`，但仍计划留到 P4 重写的 `wave4a-public-api.test.js` 与 `wave3-properties.test.js` 顶部直接 require 这些 barrel。保持旧测试不动会出现 `MODULE_NOT_FOUND`。`plan.statistics.scopeActionCount` 也实际参与 compiler 控制流，删统计时必须同步替换。

**修改建议：** 把 P3 第 4–6 步改成明确的依赖组：先让 render/metrics/compiler/工厂内部读取普通类型字段和预算，再原子删除证明写入与 oracle；尚未移除的消费者全部迁完后才能删生产方。barrel 删除前在同一提交调整存续测试 import。可以保留过渡实现，但不得把恒成功桩当最终方案。每组以 typecheck + golden + 存续 unit 验证。

### R5 / Major：预算替换是已证明的行为变化，不能放入零变化重构

**位置：** 方案 `:109`、`:220`、`:296`、`:303`、`:594`。

**复现一，默认 expanded CASE：**

```js
var source = 'select ' + 'case when a then '.repeat(60) + 'b' + ' end'.repeat(60) + ' from t';
```

输入 1,275 code units，现有返回 `preserved / LAYOUT_COMPILE_RESOURCE`。临时 bundle 仅中和旧 layout 数值预算，保持其余生产逻辑，输出变为 45,075 code units；新上限为 70,636，允许这个输出。故「删旧预算 + 新上限」不是行为等价重构。

80/120/200 层分别输出 79,295 / 176,535 / 486,215 code units，都超过新上限。旧检查防的确实包括普通 SQL 的排版膨胀，不全是内部对象自卫。允许用粗预算替换，但需明确预算在生成输出时检查，避免先完整生成、join、重新 lex 大输出才发现超限。

**复现二，默认 Extract：**

```js
var source = 'select ' + Array.from({length: 12000}, (_, i) => 'c' + i).join(',') + ' from t';
```

输入 72,903，当前 `extracted` 输出 360,000；新上限 357,148，按方案会变为保留原文。该输入不是 hostile 对象，完全低于输入上限。

**修改建议：** 将资源策略调整单列为行为提交，解释 status/code/文本变化；也可以在纯重构阶段暂保留旧数值策略，稍后替换。增加几个确定性边界样本即可，不需要恢复墙钟门或完整记账预算。明确 per-target 和整批输出限制，以及 Extract 是否采用相同公式。

### R6 / Major：P4 零变化要求、K7 修复时机与缺陷清单互相冲突

**位置：** 方案 `:110–111`、`:159`、`:220`、`:254`、`:308–321`、`:534`。

**K7 真实复现，默认选项：**

```sql
select x from t order by ${p}desc
```

当前无诊断输出 `ORDER BY\n      ${p} DESC`。令 `${p}` 替换为 `score_`，原文排序字段是 `score_desc`，输出却变为 `score_ DESC`。这违反新第 5 条底线，因此按 §8 应是 Blocker，不能继续登记为 Major 并含糊放到 P3 或 P7。

保护条件还漏了模板彼此相邻：`select ${a}${b} from t` 与候选 `SELECT ${a} ${b} FROM t` 指纹相同；替换 `a=1,b=0` 后，前者查询 `10`，后者变为 `1 0`。只保护模板与「单词字符」间的插空不足，应明确相邻模板和删除原有分隔的行为。

P4 第 1 步称 K18 是唯一行为修复，第 4 步同时修 K20/K21，第 6 步修 K25–K27，验收却仍要求 golden 零变化。其中 K21 必然改输出：`CREATE TABLE t (a INT)` 当前被补结尾 LF；K25/K26 是宿主行为；K27 实为 P2 的性能门问题。

**修改建议：**

- 先独立修 K7 并更新 golden，再开始删除机制；若决定延期，需所有者明确豁免过渡期违反新底线，不能隐含批准。
- 模板周围未知的连续拼接片段整体保留；明确三层表中的「原样」指全 target 还是最小安全片段，避免修 K10 的 `db_${env}.tbl_${dt}` 与模板保护互斥。
- P4 分为 adapter 纯重构与 K18/K20/K21/K25/K26 行为修复，每个提交有各自验收；更正 K27 阶段。零变化范围同时包含 status 和诊断 code，不只是文本。

### R7 / Major：P6 的 CTAS 目标需要结构建模，通用空格层不会格式化 SELECT

**位置：** 方案 `:158`、`:332–336`、`:539`。

**复现，默认选项：**

```sql
create table t as select a,b from src
```

当前返回原文；analysis 中只有覆盖整句的 `hive-ddl` opaque，`queries().length === 0`。按照 §5.3 只调整同一行 token 空格且保留换行，只能得到类似 `CREATE TABLE t AS SELECT a, b FROM src`，无法得到已建模 SELECT 的列列表、FROM 分行；现有三个 layout 接入点不会凭空产生 query 节点。

**期望：** 若 K12 的关闭定义是内部 SELECT 按普通查询完整排版，必须具备外壳与 query 的真实边界。

**修改建议：** 二选一：明确 CTAS 外壳的最小 parser/CST 边界建模并把 SELECT 接入现有 query layout；或把 P6 目标收缩为整句通用规范化，将完整 CTAS SELECT 排版继续列为功能缺失。不能通过搜 `AS SELECT` 或局部正则猜边界。典型 CTAS 加 golden，含列定义、字符串/注释中的同名词及 query 内 CTE。

### 必须先修订的 Blocker 和 Major

#### S1 / Major：模板与运算符相邻仍能改变替换后的 SQL，粘连规则检不出

**位置：** 方案 `:105`、`:129`、`:328–333`；当前 `src/core/api/format.ts:318` 的等价校验与查询 layout。

**默认 Hive、upper 的实际复现：**

```sql
select x from t where ${lhs}=1
```

当前输出：

```sql
SELECT
      x
FROM t
WHERE ${lhs} = 1
```

令 `lhs=x>`，原文替换后为 `where x>=1`，输出替换后为 `WHERE x> = 1`。本机再次 lex 替换后的两段，前者有一个 `>=` operator，后者是 `>`、`=` 两个 operator。替换前 token 指纹相同，附录 E 粘连检查为 **0**：`parameter + operator` 不在 WORD×WORD 集合内。

使用 Hive 的 `${hivevar:lhs}` 命名空间同样复现。当前五条底线的文字只保护模板内容和指定种类的边界，并未禁止这里的 gap；因此按 §8 列为 Major 的模板场景缺口，不声称现有粘连公式已违规。它说明需要补充保护范围，而非扩大公式的成功声明。

**期望：** 未知模板展开值时保留 `${lhs}=1` 的连续边界；可以格式化外部 SELECT/FROM，不插入这个空格。

**建议：** 对含模板的连续片段保留边界，覆盖模板与 operator、punctuation、string、quoted-identifier 相邻，而不只单词类。没有必要推断变量值；模板边界不能证明安全时保留最小片段或 target。加入上述真实输入与替换前后对照 golden。这不是 hostile 输入，是 Hive 文本替换的正常使用。

另有定义错误：方案说“相邻两个 code token”，但 `parameter.channel === "protected"`。附录 E 实现实际保留了所有非空白 leaf，才能检出 `${p}desc`。实现若据正文过滤 `channel === "code"`，K7 会再次漏检。应明确“相邻非空白 leaf，包含 protected parameter”，并保留注释作为边界，避免跨注释错误配对。

#### S2 / Blocker：通用 keyword 转换会改写大小写敏感的用户名

**位置：** 方案 `:182–191`、附录 F Q1 `:877`。

**默认 Hive、upper 的复现与规则推演：**

```sql
show role grant user string
grant role r to user string
```

当前 formatter 两句均保持原文。按修订通用规则，仅把 lexer keyword 转大写，会输出：

```sql
show role grant user STRING
grant role r to user STRING
```

`string` 在本项目是 keyword，Hive 中又是可作为 principalIdentifier 的 nonReserved 词。候选输出的 token 指纹相同、粘连违例为 0；用户名却从 `string` 变成 `STRING`。不是所有未引用的名字都遵循表名/列名的大小写规则。

**期望：** 保留用户名 `string` 的原始字符，只转换确认属于 SQL 语法的位置。

**建议：** 将 USER/GROUP principal 名、授权相关载荷纳入保护；尚未确认这些语法位置时整段 preserve。不能用“keyword leaf”作为字符串语义的证明。增加同名非保留字和混合大小写 principal 用例。

**证据边界：** 本机验证了分类和规则候选，未运行 Hive/metastore。Hive 4.0.1 的 [principal 语法](https://github.com/apache/hive/blob/rel/release-4.0.1/parser/src/java/org/apache/hadoop/hive/ql/parse/IdentifiersParser.g) 允许该词；[AuthorizationParseUtils](https://github.com/apache/hive/blob/rel/release-4.0.1/ql/src/java/org/apache/hadoop/hive/ql/parse/authorization/AuthorizationParseUtils.java) 原样取名字，[HiveAuthorizationTaskFactoryImpl](https://github.com/apache/hive/blob/rel/release-4.0.1/ql/src/java/org/apache/hadoop/hive/ql/parse/authorization/HiveAuthorizationTaskFactoryImpl.java) 将它传给角色查询；[ObjectStore](https://github.com/apache/hive/blob/rel/release-4.0.1/standalone-metastore/metastore-server/src/main/java/org/apache/hadoop/hive/metastore/ObjectStore.java) 以 principalName 查询，未在该路径统一转大小写。这里按附录 F 的明确要求将此反例列为 Blocker；候选不冒充尚未实现的通用层实际输出。

#### S3 / Major：CTAS 全句唯一 AS 规则误把 CTE 的 AS 当作第二候选

**位置：** 方案 `:454–457`；附录 F Q4 `:880`。

**复现：**

```sql
create table t as with q as (select a from src) select a from q
```

按文中 token/括号规则，本机得到两个候选：offset 15 的 `AS WITH`，offset 25 的 `q AS (`。两个 AS 都在深度 0、前面不是 STORED、后面属于查询起始集合。因此“候选不止一个则整句保留”会保留这条合法 CTAS，而 P6 又明确要求查询内带 CTE、关闭 K12。

**期望：** offset 15 是 DDL 外壳终点，后面的 AS 属于 query；查询交给 `parseQueryRange`，正常排版。

**建议：** 从语句头解析/消费支持的外壳，识别终止外壳的 AS 后立即进入 query parser；不再扫描 query 内部寻找竞争候选。无法完整消费外壳则 preserve。保留完整消费和查询 parser 的 trial/depth 边界。只找“第一个 AS”也不够，应结合明确的外壳字段；FROM 开头和括号查询是否属于 CTAS 子集需按目标 Hive 语法明示。

本机复现的是方案候选算法，不是未来 CTAS parser。Hive 的 [CreateDDLParser](https://github.com/apache/hive/blob/rel/release-4.0.1/parser/src/java/org/apache/hadoop/hive/ql/parse/CreateDDLParser.g) 在外壳后直接消费 `AS selectStatementWithCTE`，无需查询内部唯一 AS 条件。

### T1 / Major：模板片段停在逗号等符号，仍会改写替换后的字符串

**位置：** 方案 `:107`、`:137`、`:348–355`、附录 E `:883–901`、F.2 Q5 `:988`。

**复现，默认 Hive、upper、leading comma：**

```sql
select ${hivevar:left},${hivevar:right} from t
```

当前实际输出：

```sql
SELECT
      ${hivevar:left}
    , ${hivevar:right}
FROM t
```

令 Hive 变量 `left` 的值为 `'a`，`right` 的值为 `b'`（值包含所示引号字符）。这是普通文本替换：

- 原文展开：`select 'a,b' from t`，一个字符串 literal；
- 输出展开：`SELECT\n      'a\n    , b'\nFROM t`，字符串内容增加换行、缩进与空格。

本机 lex 展开后的文本，字符串 raw 分别为 `"'a,b'"` 和 `"'a\n    , b'"`，确实不同。**附录 E 原脚本对未展开文本的检查：单词类 0、模板片段 0**。两模板被逗号隔开，各自成为单 leaf 片段；P1b 现有原子规则不会保护逗号两侧新写入的空白。

**期望：** 未知变量展开值时，保留该原文或足够大的安全 source slice，使展开后的字符串仍为 `'a,b'`。

**根因：** “没有以逗号开头/结尾的多字符 token”只适用于已确定的 SQL code 上下文；模板可能引入引号、注释开头，使逗号落在字符串/注释内部。括号、分号以及作为片段边界的原有空白也存在同一种上下文问题。仅删掉四个 STOP 符号，不能证明所有未知展开值都安全。

**建议：** 在方案里明确 `${…}` 的展开契约与保留范围。最小实现选择是：没有展开值或明确语法保证的 unquoted 模板，保留完整 target；后续只在可证明的场景开放局部排版。仅保留单个 statement 也要证明替换不会跨分号改变词法上下文，不能在边界继续写入未知安全的空白。若所有者接受仅支持完整标识符/数值等展开值，也必须列为明确的产品约束和所有者待定项，不能从现有 D1–D12 或“个人使用”推导出限制已获批准。无需获取真实变量或引入外部 SQL 执行。

把此用例补入 P1，记录 glue 的盲区；修订 P1b 的保护与允许 golden 变化范围，验证输出原样或明确的保留策略。不要把“两个规则为 0”作为该用例语义安全的证据。

**严重度依据：** 本次未展开的字符串/parameter leaf 字符与方案现有片段公式都没有直接违规，所以按第二轮 S1 的同一口径列 Major 的模板语义缺口，**不升级为 Blocker**。反例是可展开为合法 Hive SQL 的字符串拼接，不是 hostile 对象或恶意 workspace 配置。

**1. lexer 合成原子：接受这项实现调整。** `src/core/lexer/lossless-lexer.ts:1067–1117` 的合并单位是包含模板的连续可吸收 leaf 区间。空白、换行、注释属于 trivia，四个停止符只按 punctuation 的完整 raw 判断；`.`、运算符、方括号、引号 leaf 可以被吸收，与 §4 按 leaf 定义的零宽邻接一致。字符串、引号标识符内部出现的 `${…}` 不会单独启动合并；它们紧邻一个真正模板时，原始文本随整个片段保留。合并后重新编号，span 覆盖原始区间，raw 直接切原文。

为避免仅用合并后的 lexer 验证自身，在独立内存模块中关闭最后的合并调用，保留扫描结果；再从每个模板向左右按 §4 的停止条件推导片段区间。**7,032 个输入、7,609 个片段**的区间、protected channel、原文拼接、raw/span 和连续 id 全部通过。输入包括四种停止标点、空格/tab/LF/CRLF、两类注释、连续模板、嵌套模板、标识符前后缀、运算符、方括号、Unicode、字符串和引号标识符。

**2. token 等价加 glueKept：完整保护成立，分类存在上述 Minor。** 合成 parameter 的 raw 不获关键字大小写授权，拆开或改写其内部会被 token 检查拒绝；`:322–335` 的 `glueKept` 保留相邻单词 leaf 的空白有无，并禁止删除模板与外侧 leaf 之间已有的空白。模板旁是 `,`、括号或注释时，删除空白不会改变 token，但会被 glue 检查拒绝；模板吞并可吸收邻居时，由 token 检查的 mismatch 路径拒绝。

额外把 12 个定向候选送入实际检查函数：片段内部插空白、改大小写、相邻模板拆开均报 token；两侧空白删除、模板旁逗号/括号/注释空白删除以及 `0L` → `0 L` 均报 glue。golden runner 保留了完整片段规则，手工未合并 leaf 的自检也继续有效。

### P2-R1 / Major：tag 查询失败被当成“tag 不存在”，发布继续执行

**位置：** `.github/workflows/build-vsix.yml:72–78`，尤其 `:76`；要求见方案附录 B 的 release job。

当前写法为 `test -z "$(git ls-remote --tags origin "refs/tags/${tag}")"`。远端查询因网络或认证错误退出非零、stdout 为空时，外层 `test -z` 仍返回 0；`set -e` 和 runner 的 `pipefail` 都不会因此终止。于是尚未确认 tag 不存在，就继续调用 `gh release create`。这是可复现的错误处理分支，不是理论竞态，也不涉及恢复已删除的发布溯源机制。

**最小复现，仅使用本地 shell 函数，不访问 GitHub、不创建 Release：**

```sh
bash --noprofile --norc -e -o pipefail <<'SH'
set -eu
git() { echo 'fatal: unable to access origin: simulated network error' >&2; return 128; }
gh() { printf 'PUBLISH WOULD RUN: %s\n' "$*"; }
tag=v9.9.9
test -z "$(git ls-remote --tags origin "refs/tags/${tag}")" || exit 1
gh release create "${tag}" fixture.vsix --target review-sha
SH
```

**实际：** 打印 fatal 后仍打印 `PUBLISH WOULD RUN: release create v9.9.9 fixture.vsix --target review-sha`，整个 shell 退出 0。**期望：** 查询失败就退出非零，不调用发布命令。

另从当前 workflow 原样提取整个 run 块，在本地 fixture 中分别提供三种 git/gh 桩：tag 存在时退出 1 且不发布；不存在时正常调用发布；查询错误时错误地退出 0 并调用发布。已有 Release 仍不会因这段代码被覆盖，但如果已有 tag 尚未建立 Release，`gh release create` 可以为已有 tag 建立 Release，不能代替这里的“只允许 tag 尚不存在”检查。

**修改建议：** 先在独立命令中保存查询结果，让失败状态传给 `set -e`，再检查空结果：

```sh
tag_refs="$(git ls-remote --tags origin "refs/tags/${tag}")"
test -z "$tag_refs" || { echo "${tag} already exists" >&2; exit 1; }
```

仅在临时脚本中试用该建议后，三种分支分别得到：tag 存在退出 1、不存在正常发布、查询错误退出 128 且不发布。仓库 workflow 未修改。
