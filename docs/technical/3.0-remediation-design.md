# SQL Beautify 3.0 工程审计整改设计

状态：已批准实施

目标版本：`3.0.0`

设计基线：`bc08772`（`2.0.1`）

审计输入：[`engineering-review-2026-07-26.md`](engineering-review-2026-07-26.md)

## 1. 目标与约束

本设计一次性处理 2026-07-26 工程审计中确认的正确性、性能、诊断、主机适配、
可维护性、回归语料和能力覆盖问题。所有改动先在本地按可独立回退、可独立验证的波次落地，
最终统一形成一个 `3.0.0` 发布候选；中间波次不修改为可发布的小版本，也不触发远端发布。

以下约束不因整改而放宽：

- lexer 仍是 source span 的唯一权威，renderer 仍是格式化空白与 keyword case 的唯一写入者；
- comment、string、quoted identifier、parameter、dialect literal、opaque/verbatim slice 必须 lossless；
- source map、range、multi-selection、worker、DDL 继续 fail closed、all-or-nothing；
- worker 回传、direct core 回传和 host commit 前的边界校验不得因性能优化而抽样；
- 不恢复旧 formatter、bridge、root shim、额外公开 internal export 或第二套生产实现；
- 设计中没有待用户确认项。测量结果只能在预先写明的安全边界内选择保守值，不能扩大范围。

## 2. 固定设计决策

### 2.1 版本与兼容边界

统一发布版本为 `3.0.0`。major 的理由不是单一 API 破坏，而是以下行为契约同时变化：

- CRLF 与 BOM 成为受支持的 lossless 输入边界；
- `preserve` 从“完全无反馈”改为“不发布 capability 波浪线，但命令给出一次安全提示”；
- VS Code 生产路径只保留资源级 `sqlBeautify.dialect` 这一份 dialect 权威；
- 超大输入会在确定边界立即 preserve/reject，而不再无上限执行；
- direct/worker 路由阈值、worker 排队 deadline 和取消生命周期改变；
- 新增 Hive `INSERT INTO ... SELECT` 与 `SET` 的结构化支持。

公开包入口仍只有 `formatter`、`experimental/ddl` 和 `package.json`。现有 `formatSql`、
`lexSql`、`formatHiveDdl`、`extractDdl` 函数名与参数形式保持不变。

### 2.2 EOL 与 BOM

renderer 使用独立内部 `RenderEnvironment.newline`，不把 newline 加进公开 `CanonicalFormatOptions`。
public document API 从源文本第一个 newline leaf 推断（`\r\n`、`\n` 或 lone `\r`），无换行输入
缺省使用 `\n`；transaction 从完整文档推断后透传给 fragment，VS Code 在无物理换行时用
`document.eol` 补足环境。所有 generated line break 使用同一 EOL；verbatim 内原始 EOL 不改写。
`RENDER_NEWLINE_CONTRACT` 同时验证边界换行数量和 generated EOL 一致性。

offset 0 的 U+FEFF 由 lexer 发射为独立 `byte-order-mark` trivia leaf，并作为不可改写的
source emission 保留。其他位置的 U+FEFF 继续是 unknown/protected，防止把嵌入式字符误当边界。

### 2.3 trailing comma 与 source-map 顺序

采用审计报告路线 A：若某个 list boundary 的 source 顺序是“左 item → trailing line comment →
separator”，即使全局 `commaStyle=trailing`，该 boundary 也局部使用 leading comma。
其他无冲突 boundary 仍使用 trailing comma。

不采用 source-map 路线 B。source/output 双单调契约、selection mapping 和 token equivalence 保持不变。
ADR 记录路线 B 的拒绝理由与重新启用条件：只有路线 A 被真实用户证明不可接受，且能为非单调
source run 给出完整映射证明时，才允许另起设计。

### 2.4 输入、路由与 worker SLO

生产格式化请求的最大完整文档/target 为 524,288 UTF-16 code units（512 Ki code units）。
选择该值是因为审计实测 513 KB worker 路径约 6 秒、maxRSS 759–928 MB，而 1 MB 已达到
11.82–12.51 秒、1.48–1.72 GB；512 Ki 先把单请求风险限制在已测的较低档位。
该限制是风险边界，不宣称为普适 UX 上限。超限返回稳定诊断码并保留完整原文。

本机回归目标：

- direct 路径只处理 `< 8,192` code units 且 `< 2,000` leaves 的请求；多形态基准 p95 目标 150 ms；
- 512 Ki worker 请求在独立进程中 10 秒内完成、maxRSS 不超过 1.25 GB；
- 任何排队请求从 enqueue 起共享 60 秒总 deadline，不能在出队后重新获得完整 60 秒；
- active cancellation 给 worker 200 ms drain grace；窗口内自然完成则复用 worker，超时才 terminate；
- queue source-code-unit 背压继续保留，不能被单请求上限替代。

阈值必须同时由源码长度与 leaf 数限制。unknown run 合并会降低 leaf 数，因此与阈值变更在同一
性能波次验证。`snapshot.source.length >= leafCountThreshold` 只是 `leaves <= code units` 的
安全下界剪枝，代码中必须写明单位与不变量。

### 2.5 range 校验执行位置

`Format Selection` 的完整文档结构校验改为 executor 能力，而不是 transaction 主线程中的同步调用：

1. transaction 先完成 primitive shape、非重叠、source boundary 等廉价检查；
2. 存在非空 fragment 时，executor 接收一次完整 document + 全部 targets 的
   `validateAndFormat` batch 请求；
3. routed executor 对微型文档走 direct，对其余文档走同一个 persistent worker；
4. worker runtime 先以 document mode 校验完整源，再按各 target 的 fragment mode 格式化 slice，
   一次回传 target 集严格一一对应的结果；任一失败整批拒绝。

range 校验的 document-mode artifact 与 fragment formatter artifact 不缓存、不互换。
跨线程消息继续绑定 generation、documentVersion、source digest、runtime digest 和 request identity。

### 2.6 diagnostics 与内部排障信息

用户诊断采用显式安全码表：仓库内所有可到达 diagnostic code 都有不含 SQL 片段的静态消息；
有 `capabilityId` 时只附加经过格式校验的 capability identity，不添加 adapter 无法证明的方言名。
同 target、code、capability 下相互包含的 span 只保留最小可操作 span。

`unsupportedSyntaxPolicy=preserve` 仍抑制 capability editor diagnostics，但显式命令在 unchanged/rejected
且存在 capability 证据时显示一次 information message；`hive-ddl` 给出专用 DDL 命令提示。
provider/format-on-save 不弹窗。

内部异常采用独立、受控且 opt-in 的 `DebugEvent` execution channel，而不是改动公开 `FormatResult`、挂未登记字段，
或使用无法跨 worker 的 callback。core 同步 collector 进入内部 execution outcome，direct/worker protocol、
transaction 和 `debugDiagnostics` console summary 逐层验证并透传。event 只包含阶段、稳定 code、异常类型
和最长 512 字符的 error message、经清洗的调用帧：stack 首行不重复收集，路径限制长度，帧数和总长度
均有上限。`debugDiagnostics` 文档明确说明 opt-in console 可能包含 SQL 片段与本地路径；editor message、
clipboard 安全报告永远不包含 debug event。

### 2.7 host 与 DDL 一致性

- 文档关闭时同时删除 diagnostic generation 和 `DiagnosticCollection` 条目；
- `publishDiagnostics` 每次发布只读取一次文档长度；
- selection 恢复对 output 建一次 line-start index，以二分映射 anchor/active；selection→target owner
  使用排序游标，不再为每个 selection `find` 全部 targets；
- DDL target 校验单次遍历 leaves，line prefix 使用预建行首索引；
- transaction edits 先排序校验，再用 chunks/join 单次构造 output，避免 multi-selection O(n·m) 拼接；
- query/DDL 共用 host commit 预演与 edit range 校验。query 继续用 source map 做语义 selection 恢复；
  DDL 无 source map，只使用显式的 offset/delta/clamp 映射并保持方向，不能声称与 query 等价；
- 删除 test-only `adapter-contract.ts` 及未进入生产的 `SupportedLanguage.dialect` 字段，把测试改为覆盖
  `extension.ts` 实际入口；生产仍由 resource-scoped `sqlBeautify.dialect` 单点决定方言。

### 2.8 statistics、snapshot 与 invariants

`FormatPipelineStatistics` 使用一个内部 mutable accumulator，出口统一冻结快照。失败路径保留此前
已计算的 leaf/node/plan/render 数值，不再通过 16 个位置参数和 `0` 占位重建。

第一次 core→adapter 或 worker→adapter `snapshotFormatResult` 仍执行深拷贝和验证；产物写入模块私有
`WeakSet` brand。transaction 的第二次 snapshot 命中 brand 后复用冻结对象，但仍针对当前 source
执行 `isFormatResultSafeForSource`。任何 structured-clone/raw object 都不能绕过第一次校验。

invariants 保持“每次解析全量证明”。本轮不做 statement 抽查，也不删除关系校验。结构治理采用：

- 单一 node-kind registry 汇总 kind、子节点关系、marker/capability/context validator family；
- 编译期穷尽性与运行时测试确认每个 `SyntaxNode["kind"]` 都有 registry entry；
- 新增节点 checklist 与生成/校验脚本防止遗漏 5–6 个 invariant family；
- 对融合遍历只做有基准的机械合并，不改变失败码和证明语义。

### 2.9 alignment 与 source-map 规模

alignment 第二遍保留，因为它依赖第一次 render 的真实行列。优化只收窄投影：先从 list item 收集
AS/comment candidate 及相关 item leaf range，再为候选 leaf 建 source-map lookup 和 item shape；
`outputLineStarts` 仍线性扫描完整输出。验收以 0-target false-positive 合成样本的阶段耗时下降为准，
不能用“候选 leaf 占 6.7%”直接推导耗时比例。

source-map 治理先用独立进程 heap profile 区分 source map、analysis index、renderer 临时对象和
structured clone 占比。无论归因结果如何，都增加 entry 数/clone 时间基准和显式 renderer entry budget；
本轮不改变 source-map 外部形状或双单调语义。若 profile 未证明 source map 是主因，不做猜测性压缩。

### 2.10 lexical profile

identifier start/continue 进入 `LexicalProfile`：

- `hive` 与 `generic` 保持现有 ASCII contract；
- `postgresql` 使用 Unicode identifier letter/mark/number 规则，并保留 `_` start、`$` continue；
- `mysql` 按其 unquoted identifier contract 接受 ASCII alnum/`_`/`$` 与 U+0080–U+FFFF，
  不把 whitespace、delimiter 或 supplementary code point 猜成 identifier；
- 连续 unknown code points 合并为一个 protected leaf，仍精确覆盖原 source span。

每个 dialect 都补正反例、quoted identifier、CJK、combining mark、supplementary code point 和
token-equivalence 回归。Hive 的裸中文标识符仍 preserve，不用“用户常见”覆盖方言规范。

### 2.11 能力覆盖

本次实现 Hive `INSERT INTO [TABLE] target [PARTITION (...)] SELECT/WITH ...`，复用现有
`INSERT OVERWRITE` 的 target/partition/query 结构，并为 capability registry 增加独立 identity。
实现 Hive `SET key=value` / `SET key` / `SET` 的有界 statement 节点与 layout；value 作为可证明的
verbatim assignment payload，不做类型或变量语法猜测。

审计列出的 `EXPLAIN`、`GROUPING SETS`、`TRANSFORM`、主命令 DDL、`UPDATE`、`DELETE` 不在报告的
实施优先建议中，也没有完成语法设计。它们仍纳入 3.0 的显式处置：继续由 capability matrix 标注
为 recognized/preserved，补精确公开回归和用户提示，不在本轮伪装成“支持”。主命令遇到 Hive DDL
时提示专用 experimental 命令。只有 `INSERT INTO` 与 `SET` 从 preserved 提升为 formatted。

### 2.12 公开语料与文档

公开 corpus 改为清单驱动，至少包含：多 KB CTE/window/CASE、中文注释、line comment、CRLF、BOM、
trailing comma fallback、CJK identifier dialect matrix、INSERT INTO、SET，以及明确 preserved 的
EXPLAIN/GROUPING SETS/TRANSFORM/DDL/UPDATE/DELETE。测试断言精确文件清单、options、状态、幂等性、
token equivalence 和 EOL/BOM 保留，不再只断言 `>= 5`。

README 写明 verbatim 不参与 keyword case、超大输入边界、preserve 命令反馈和 DDL 命令选择。
架构文档升级为 3.x 契约；新增 `docs/migration-to-3.0.md`，不把内部波次计划复制进 README。

## 4. 失败与回退策略

- 任一波次 targeted gate 不通过，不创建该波次完成提交；先在同一波次修复。
- 性能测量若受单次噪声影响，使用独立进程、预热、至少 9 次取中位/p95；不通过放宽阈值时，
  只能把更多请求路由到 worker或降低输入上限，不能删除安全校验。
- private corpus 不存在时明确记录 skipped；公开 corpus 与完整长期门仍必须通过。
- source-map profiling 若不能稳定归因，只交付测量工具、budget 与“暂不压缩”的结论，不实施猜测性重构。
- 路线 A、输入上限和 preserve feedback 都可通过各自聚焦提交回退，不要求回退其他波次。

## 5. 发布完成定义

`3.0.0` 发布候选必须同时满足：

1. 处置矩阵每项有代码、测试、测量或 ADR 证据，无“待确认”；
2. 每个实施波次有聚焦本地提交，工作树除忽略的 build/package artifact 外干净；
3. `npm run test:verify`、private corpus（若可用）、独立 worker 性能/内存门全部通过；
4. `npm run verify:clean-package`、`npm run package:vsix`、`vsce ls`、release boundary、
   support-matrix generator write/check、`git diff --check` 全部通过；
5. package、lockfile、CHANGELOG、migration link、VSIX 文件名/manifest 全部为 `3.0.0`；
6. 本地不 push、不建 tag、不创建 GitHub Release、不触发 workflow release job。
